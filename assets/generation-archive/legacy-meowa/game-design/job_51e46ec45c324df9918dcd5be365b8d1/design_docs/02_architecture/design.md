# 系统架构

## 架构目标

以 Phaser 3 + TypeScript 制作浏览器优先的单场景 Demo。架构重点是快速迭代、确定性更新、数据与表现分离，以及在不引入联网需求的前提下让技能、兵线和 AI 易于调参。

## 系统地图

输入与镜头 → 玩家控制；玩家控制与 AI 控制 → 单位/战斗模拟；兵线调度 → 单位/战斗模拟；战斗模拟 → 技能、生命、塔与核心状态；所有状态 → HUD、特效与音频反馈；比赛状态机统筹开始、战斗、胜负、重开。

## 系统职责

- **比赛状态机**：初始化、进行中、英雄重生、胜负结算、重开；禁止各对象自行决定整局结束。
- **输入与玩家控制**：鼠标点地、目标选择、普攻目标、Q/W/E；将输入转换为意图，不直接修改生命或胜负。
- **单位与移动**：英雄、小兵、塔、核心的空间位置、碰撞半径、路点移动和攻击距离。
- **战斗与技能**：攻击冷却、投射物/范围判定、伤害、减速/减伤、死亡与重生事件。
- **兵线与塔**：定时生成波次、固定路点、仇恨优先级、塔与核心的耐久。
- **AI 控制**：有限状态机，按血量、距离、兵线和技能冷却选择补刀、换血、后撤、推线。
- **表现与 HUD**：血条、冷却、补刀、提示、特效和结果画面；只读取状态，不承载规则。

## 依赖关系

核心规则不依赖 Phaser 场景节点以外的表现对象；所有单位使用统一的实体数据和事件接口。寻路不采用通用 NavMesh：中路是固定可行走带，英雄使用点到点移动/局部 steering，小兵使用路点。未来若扩展障碍物，再替换移动实现，不改变战斗接口。

## 资源、状态与信息流

输入产生玩家意图；控制器写入单位目标位置或技能请求；模拟器按固定逻辑步更新位置、冷却、攻击和生命；事件总线发布命中、死亡、补刀、塔受击和比赛结束；HUD/特效订阅事件并读取只读状态。数值集中在 TypeScript 数据表中，避免散落在场景脚本。

## 核心循环覆盖

玩家控制覆盖走位与施法；单位/战斗覆盖补刀和换血；兵线/塔覆盖推线与推塔；AI 覆盖对手压力；比赛状态机覆盖胜负与重开；HUD 覆盖玩家对因果的理解。

## 系统边界

不引入联网同步、后端、账号、物品数据库、通用行为树、动态导航网格或完整物理模拟。Phaser 3 的定位是渲染、输入、场景和基础 2D 能力；MOBA 特有的目标选择、仇恨、兵线、技能判定和 AI 自行实现。

## 优先级与范围

推荐 **Phaser 3 + TypeScript + Vite**。它原生面向浏览器，分享成本最低，TypeScript 与数据驱动逻辑适合本项目；固定中路不需要 Godot/Unity 的高级寻路。Godot 4 的编辑器、2D 节点、UI 和导航更完整，但 Web 导出与团队熟悉度是额外风险；Unity 6 的生态最强，但编辑器与 WebGL 构建体量对短周期浏览器 Demo 不划算。若目标临时改为桌面独立包或开发者不熟悉前端，Godot 4 是备选；Unity 6 不作为本项目首选。

## 开放的结构问题

若首周发现 Phaser 场景代码快速失控，立即冻结内容，抽出 `GameState`、`Entity`、`AbilitySpec` 和事件接口；不要以更换引擎解决架构问题。若浏览器兼容性出现阻塞，先固定 Chromium/桌面浏览器验收，再考虑 Godot 桌面导出。
