# 像素冰桥画面持续优化计划

更新日期：2026-10-14。适用版本：Phaser 3.90.0、TypeScript、Vite；主要验收入口为 `/?map=howling`。

目标是在保留像素角色、清晰走位空间和技能判读的前提下，提升冰桥的空间层次、材质质感与战斗表现。优先修整地图构成和角色融入感，再增加局部效果；目前无需为这些目标迁移到 Three.js 或升级引擎。

本计划承接已有画面优化工作，并作为后续迭代的状态入口。状态“已接入”表示代码已存在，不等于最终美术质量或性能已经验收。未实施条目是候选任务，不自动改变玩法或启动资源生成。

## 必须保留的方向

- 技能释放及投射物附带的动态照地光已按用户要求移除，不因后续优化重新启用。技能动画、刀身效果和命中反馈不是这一项。
- 保留防御塔、泉水的环境照明，但不能洗白角色或压暗战斗信息。
- 像素边缘优先清晰，不用全屏模糊掩盖资源不一致。角色锚点、尺寸、方向和动作衔接问题需要单独修正。
- 画面优化不改伤害、射程、冷却、碰撞、兵线或地图通行规则；若确实需要改变，另列玩法任务。
- 环境装饰不能误导可走区域。草丛画面和草丛隐蔽机制分别验收。
- 新效果必须能独立关闭；暂停、重开和场景切换不能留下残影或重复对象。

## 引擎能力与候选任务

优先级：P0 为稳定性和可读性基础；P1 为下一阶段重点；P2 为基础完成后试验；P3 为低优先或暂缓。成本为相对工程复杂度，不是工期承诺。

“原生”表示引擎有对应 API，仍需项目接入；“组合实现”表示利用精灵、深度、遮罩等基础能力编写逻辑；“自定义”表示需要自己的渲染或着色器实现。WebGL 效果必须准备关闭或简化回退，不能默认 Canvas 同样支持。

## 验收与性能预算

以下为建议目标，尚不是当前性能测量结果。第一次执行 A 时记录设备、浏览器、窗口、DPR、镜头倍率和实际基线，再据此调整预算。

- 在选定桌面测试设备上以 60 FPS 为目标；记录 60 秒对线的帧耗时中位数和 P95，目标 P95 不高于 20 ms。加载阶段单独记录，不混入稳定对局统计。
- 同条件新增一批效果后，若 P95 比基线恶化超过 10%，先分析开销，再降低密度、分辨率或关闭该效果，不以主观流畅代替测量。
- 连续重开 5 次，检查纹理、GameObject、事件监听与灯光数量是否回到稳定范围；排查持续增长，不要求浏览器内存瞬间归零。
- 单项效果要记录活动数量、峰值、更新频率和可见区域策略。全屏透明叠加、模糊、辉光和大纹理须单独测量。
- 当前冰桥地面整图为 6200 × 3400；单份 RGBA8 约 80.4 MiB，半分辨率法线约 20.1 MiB，尚未计入 CPU 副本、临时高度数组和驱动开销。分块方案要同时验证接缝、采样和法线，不只降低数字。
- WebGL 不可用时不得因照明或 FX 报错而阻断游戏。自定义效果提供简化贴图或关闭回退；Canvas 路径需实际测试后才标记通过。

固定验收场景：蓝方泉水、红方泉水、中央兵线、沿两侧桥缘移动、八方向绕塔、Q/W/E/EQ/Q3/R、停止与转向、暂停恢复、连续重开，以及技能练习页返回冰桥。

每项需检查：前后景遮挡、血条与目标辨识、施法方向、透明边缘、像素清晰度、低档可读性。纯表现改动不得改变战斗事件时间或结果。涉及代码时运行 `npm test` 与 `npm run build`；通过测试不替代实机视觉验收。

## 维护方式

状态统一使用：待做、试验中、待验收、已接入、已验收、暂缓、已移除。每次完成任务同时更新能力表和下方记录；不要把“已经接入”直接改为“已验收”。

新任务按以下字段登记：

| 字段 | 填写要求 |
| --- | --- |
| 任务 | 对应 V 编号、要解决的画面问题、负责人 |
| 范围 | 地图或角色、是否只在冰桥启用、不改哪些玩法 |
| 实现 | 原生 API 或自定义模块、资源依赖、兼容回退 |
| 参数 | 默认值、单位、开关、低中高档差异 |
| 验证 | 同视角前后截图或短录屏、帧耗时、测试与构建结果 |
| 结论 | 保留或回退、尚存问题、下一步、更新时间 |

建议把后续截图和测量放在 `docs/visual-validation/YYYY-MM-DD/`，该目录在首次验收时创建。效果配置后续可集中到独立模块；本次仅制定计划，不创建运行时配置或修改游戏表现。

- 地面仍遵循锁定镜头或按住空格开启平滑、自由镜头关闭的规则。没有恢复施法照地光。
